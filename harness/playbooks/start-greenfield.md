# When

The repo has no source yet, or the task asks for a new service or application. Applies when the task says "choose your architecture" too ([DEL.4](../rules/delivery/del-4-a-new-service-starts-with-its-design.md)). Not for a change to an existing service: its own shape is the convention ([scaffold-from-conventions](scaffold-from-conventions.md)).

# Steps

1. **Scaffold.** `tvh greenfield init --target . --profile service` (`--profile web-app` for an HTTP application, which is judged on ports and a health endpoint rather than on run sources and stores; `--profile generic` for a repo that runs no operations) writes the design skeleton, the repo's `AGENTS.md`, and the project verify (kept in `~/.golden-path-harness/projects/<repo-id>/`, not in the repo), and never overwrites. the project verify runs the design gate (`tvh greenfield check --raw --`) and the [CODE.5](../rules/code/code-5-one-responsibility.md) checker; it fails until the design is filled in and the code follows it.
2. **Load the rules, at the start and again when code exists.** Open [index.md](index.md), then run `select --brief --changed` from the base instructions, naming the paths you expect to create (e.g. `src/Orders/Order.cs`) because only the design files exist yet and they select no CODE.* rule. Run it again after the first `.cs` file is written, and before the review. Open the rules it names; [DEL.4](../rules/delivery/del-4-a-new-service-starts-with-its-design.md), [CODE.8](../rules/code/code-8-dependencies-point-inward.md), [OBS.3](../rules/observability/obs-3-operational-output-is-a-contract.md), [T.1](../rules/testing/t-1-done-means-verified.md) to [T.5](../rules/testing/t-5-behaviour-has-a-scenario.md), [SEC.2](../rules/security/sec-2-no-secrets-or-personal-data.md) and [CODE.5](../rules/code/code-5-one-responsibility.md) apply to almost every service. Name what you skipped.
3. **State what done means.** Quote the task's own requirements and acceptance criteria; they are the spec ([write-spec](write-spec.md)). Do not invent criteria. List ambiguities with the reading you took. 3a. **Count the layers.** `tvh orchestrate layers --raw -- --spec "<the task>" --report REPORT.md`. Three or more layers (backend, frontend, data, infrastructure, end-to-end tests, identity) means the work is split into bounded workloads with their own file paths, verification command and model tier ([orchestrate-workload](orchestrate-workload.md)): put the output of `tvh orchestrate plan --raw --` in `REPORT.md`, or write `Decomposition: single thread - <reason>` there. The check exits 3 until one of the two is in the report. It counts words and paths: a quick prompt to decide on purpose, not a measure of size.
4. **Fill `docs/solution-design.md`.** Answer every heading. Decide these before code, because they are expensive to change after data exists: the stored layout, what one restore point or unit contains, the identity of a run and what repeating it does, the failure model, the reason codes, the events, the retention rule, what input is never trusted.
5. **One ADR per hard-to-reverse decision** in `docs/adr/` ([DEL.4](../rules/delivery/del-4-a-new-service-starts-with-its-design.md)). Typical: stored layout, run identity and idempotency, failure semantics, retention, storage medium behind its interface.
6. **Fill the repo's `AGENTS.md`**: layout, vocabulary, current decisions. In the layout, separate entry points, contracts or models, application work and external adapters; split a growing area by its reason to change; state the permitted dependency direction. Do not use `Services/`, `Helpers/`, `Interface/` or `Shared/` as an unexplained catch-all. Then add "follow a change across boundaries" with a **checked** or **documented** mark on each entry ([CODE.7](../rules/code/code-7-linked-changes.md)), verify, when to ask. Adapt the project verify to the repo's toolchain without removing the gate steps. Initialize Git for a new standalone repository, then run `tvh verify --repo . --design`; it must pass before any file under `src/` exists ([DEL.4](../rules/delivery/del-4-a-new-service-starts-with-its-design.md): design first, not documented afterwards).
7. **Build in slices** (orchestrate-workload): contracts and models; interfaces and the composition root; one implementation per kind; the operations; the entry point. Each slice compiles and has tests in its layer ([T.3](../rules/testing/t-3-tests-run-in-their-layer.md)): unit tests per component against fakes, and scenario tests through the real entry point ([T.5](../rules/testing/t-5-behaviour-has-a-scenario.md)). Interfaces for sources, stores, clock and runners from the first slice ([CODE.8](../rules/code/code-8-dependencies-point-inward.md)). One type per file ([CODE.5](../rules/code/code-5-one-responsibility.md)). Each adapter gets one test against the real dependency (a container, an emulator) or a recorded real response in the same slice, not at the end ([T.6](../rules/testing/t-6-adapter-proven-against-the-real-thing.md)): that is where wrong field shapes and effects that arrive after the response show up.
8. **Keep design and code one story.** When the code forces a different choice, change the design doc and the ADR in the same step. A design that no longer describes the code is a finding.
9. **Verify** with `tvh verify --repo .` ([T.1](../rules/testing/t-1-done-means-verified.md)), including the format check.
10. **Report** in `REPORT.md`: what matches the design, where the code diverges and why, rule IDs applied, rules consciously not applied, what was not verified. Do not claim a rule you did not check.

# Boundaries

A design is the content of the choice, not ceremony: short, specific, and true. Do not copy a design from a neighbouring repo; read it for questions to answer, not for the answers.

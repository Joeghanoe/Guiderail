This is a preliminary interpretation of the six supplied PDF exports, not a change to company principles, approved exceptions, or enforcement. Page numbers below refer to PDF pages. A principle expresses a durable intent or trade-off; a work instruction specifies a process, product, configuration or implementation. A mandatory instruction can still be binding within its stated scope without being a principle. Labels in the source do not settle the classification.

## Conflicts and decisions

External ownership never justifies omitting a dependency from monitoring. P8 records the intent; OBS.1 records concrete behavior.
- IH3/IH5 prefer asynchronous brokered communication, while IH4 contemplates follow-up queries and IH6 describes synchronous traffic through a gateway. Clarify permitted query paths and boundaries before scoring direct calls.

- Architecture A.18 disallows shared stores but permits central reporting/archive reads; Data D.10 forbids shared *write* stores and permits governed shared read models. Confirm whether A.18 has broader intended scope.
- Existing CODE.5 is human-verified as a convention linked to P-02, but no supplied PDF establishes one type per file as a company principle. A.12 concerns service responsibility, not a mechanical file layout. Keep the convention distinct and obtain approval for any new deterministic gate and exceptions.

## Advice for remaining decisions

1. **Communication scope:** retain asynchronous events for business state changes and use the governed gateway for synchronous reads and requests that need an immediate result. Document allowed paths per operation. IH4's follow-up queries need not contradict IH3, but the source owner should approve that interpretation before a grader rejects synchronous calls. Keep Event Grid routing and Service Bus delivery as distinct responsibilities rather than assuming the named products conflict.
2. **Trace correlation:** use W3C trace context for distributed execution tracing and a separate stable business/event correlation identifier where workflows span retries or multiple traces. Specify how both propagate across broker and gateway boundaries. Do not equate an arbitrary CorrelationId with a valid W3C trace identifier. Approve the contract, then verify propagation with an integration fixture.
3. **Data-store ownership:** prohibit shared mutable operational stores across service ownership boundaries; permit governed read models for reporting and analytics. P9 now records this distinction. Ask the source owner to confirm the component boundary and whether other shared read use cases are permitted before enforcing a broader ban.
4. **Framework currency:** retain DEL.2's current-or-previous stable window, consistent with the supplied Cloud document. Ask the global-instructions owner to expand the ambiguous n-1 shorthand. No live release/version determination was made in this review.
5. **Principles versus instructions:** retain product-specific choices as scoped solution instructions with ownership and versions. P2 and P11 now record this interpretation. Mandatory does not mean universal. IH11 stays future guidance; BT13's merge note remains unresolved until its owner confirms publication status.
6. **CODE.5:** preserve it as an explicitly approved convention; do not claim single service responsibility logically entails one type per file. Approve generated-file and partial-type handling before making a new deterministic enforcement gate.

The health clarification authorizes the OBS.1 rule update; it does not approve new case verdicts, evaluator thresholds or executable gates. Existing C-014 remains unchanged. A future health evaluation should cover essential external failure, partial capability failure, one-tenant failure, and a probe unable to establish health, with expected status and alert evidence approved before gating.
